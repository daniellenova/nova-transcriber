# Nova Transcriber

Проект находится в разработке.

## Назначение

Nova Transcriber — локальный сервис автоматической транскрибации аудио- и видеозаписей с сохранением результатов и истории.

## Ключевая идея

Простой, автономный и расширяемый сервис с логическим разделением способов взаимодействия, распознавания речи, бизнес-логики и хранилища. Модульность без преждевременной микросервисной архитектуры.

## Технологический стек MVP

- Python и uv.
- faster-whisper и Whisper Large-v3.
- CPU, INT8.
- Docker Compose.
- PostgreSQL.
- Telegram, aiogram и локальный Telegram Bot API.

## Архитектурные принципы

- Telegram — один из возможных интерфейсов; Core от него не зависит.
- ASR — отдельный заменяемый модуль; Core не зависит от конкретного движка.
- PostgreSQL хранит метаданные и полные тексты транскрибаций.
- Независимые Telegram Adapter, Core API и Whisper Worker; очередь в PostgreSQL.
- Перенос на другой компьютер через Docker Compose.

## Функциональность MVP

1. Получение аудио или видео через Telegram.
2. Распознавание русской речи.
3. Сохранение транскрибации и метаданных в PostgreSQL.
4. Возврат полного текста в TXT.
5. Получение предыдущих результатов через `/history`.
6. Доступ только разрешённому Telegram-пользователю.

## Направление развития

Веб-интерфейс, другие ASR-модели, удалённые вычислители и дополнительные способы обработки текста — возможные направления развития, а не функции текущего MVP.

## Локальный CLI

Положите аудиофайл в `./data` и из корня проекта выполните:

```sh
uv run --extra worker nova-transcriber "data/Запись.m4a"
```

TXT появится рядом с исходным файлом. Для локального CLI нужны Python и модель в `./models/large-v3`.

Зависимости разделены по extras: `postgres` для Core API, `telegram` для Adapter, `worker` для ASR и CLI. Образ Worker устанавливает `worker` и `postgres`; образы Core и Adapter не устанавливают ML-библиотеки. На Windows общая зависимость `tzdata` обеспечивает работу часовых поясов.

## Telegram

`MAX_FILE_SIZE_MB` в `.env` задаёт максимальный размер входящего файла: по умолчанию 1024 МиБ. Допустимо положительное конечное число, включая дробное; неверное значение останавливает запуск с ошибкой конфигурации. `MAX_DURATION_SECONDS` ограничивает длительность декодированного аудио (по умолчанию 43200 секунд, 12 часов). Существующее значение `MAX_FILE_SIZE_MB` в вашем `.env` сохраняется; для больших файлов увеличьте его вручную. После изменения пересоздайте контейнеры: `docker compose up -d --build telegram-adapter core-api whisper-worker`.

Размер из метаданных сообщения проверяется до `get_file`, фактический размер локального файла — до Core, декодирования и Whisper. При неизвестных или заниженных метаданных локальный Bot API может сначала получить файл; приложение проверяет его через `stat()`, не читая целиком в память и не удаляя из общего тома. Загрузки выполняются последовательно; перед загрузкой проверяется свободное место с учётом заявленного размера (при неизвестном размере — максимального). `MIN_FREE_DISK_MB` задаёт резерв места, по умолчанию 512 МиБ; он также проверяется перед распознаванием каждой части. Сетевые ошибки и временные ошибки сервера при `getFile` и безопасных запросах к Core повторяются до трёх попыток с задержкой. Самостоятельного скачивания и управления кешем Bot API в приложении нет.

Worker сначала потоково определяет реальную длительность записи, затем распознаёт её последовательными фрагментами по 5 минут. В памяти находится один фрагмент; временные аудиофайлы не создаются. После каждой части её текст и число обработанных отсчётов атомарно сохраняются в PostgreSQL. Прогресс в одном сообщении Telegram показывает процент и обработанную длительность по сохранённым частям. После завершения тексты объединяются в один TXT, а промежуточные строки удаляются в той же транзакции. При ошибке промежуточные результаты сохраняются.

Скопируйте `.env.example` в `.env`, задайте пароль PostgreSQL, `TELEGRAM_BOT_TOKEN` от @BotFather, свой числовой `TELEGRAM_ALLOWED_USER_ID`, а также `TELEGRAM_API_ID` и `TELEGRAM_API_HASH` с [my.telegram.org](https://my.telegram.org/apps).

Если бот уже работал через облачный Bot API, остановите прежний процесс и один раз вызовите метод `logOut` на облачном сервере перед переходом на локальный. При активном webhook сначала удалите его методом `deleteWebhook`. См. [инструкцию Telegram](https://core.telegram.org/bots/api#using-a-local-bot-api-server).

Из корня проекта выполните:

```sh
docker compose up -d --build
```

Команда запускает `postgres`, `telegram-bot-api`, `core-api`, `telegram-adapter` и `whisper-worker`. Задайте также `CORE_API_TOKEN` (случайный секрет от 32 символов). Модель должна находиться в `./models/large-v3`. Telegram Adapter создаёт задачи и получает результаты через Core API; Worker забирает задачи из PostgreSQL и выполняет распознавание. Команды `/start` и `/history` доступны разрешённому пользователю. API опубликован на `127.0.0.1:8000`, PostgreSQL — на `127.0.0.1:5433`. Исходные файлы читаются из общего volume без копирования.

Adapter опрашивает уведомления раз в пять секунд и обновляет прогресс не чаще раза в 15 секунд. Его перезапуск не останавливает Worker. После перезапуска Worker забирает прерванную задачу, когда PostgreSQL освободит её сеансовую блокировку, и продолжает с последнего сохранённого фрагмента. При возобновлении исходник потоково декодируется до сохранённой позиции; готовые части повторно не распознаются. Запись и подтверждение частей выполняются через соединение, удерживающее блокировку задачи.

Распознавание выполняется в дочернем процессе Worker. `STAGE_TIMEOUT_SECONDS` ограничивает этап подготовки, определения длительности, загрузки модели, чтения аудио и распознавания одной части (по умолчанию 3600 секунд на этап). При зависании дочерний процесс завершается; неожиданный выход процесса, временные ошибки чтения и ошибки выполнения движка также допускают до трёх повторов с сохранённой позиции, затем задача получает `failed`. Счётчик повторов сбрасывается после сохранения длительности или очередной части. При штатной остановке Worker возвращает задачу в очередь без расходования попытки восстановления. Новые поля и таблица частей создаются автоматически при запуске Core/Worker. При сетевом обрыве после фактической отправки TXT, но до подтверждения доставки возможна повторная отправка.

Перезапуск отдельного компонента: `docker compose restart telegram-adapter` (или `core-api`, `whisper-worker`). Несколько Worker: `docker compose up -d --scale whisper-worker=2`. Telegram Adapter остаётся в одном экземпляре.
