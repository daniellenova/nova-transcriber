# Инструкции для Codex

## Приоритеты

- Применяй KISS, YAGNI и DRY прагматично. Простота важнее абстрактной универсальности.
- Вноси минимальные изменения для решения задачи. Работоспособный MVP важнее преждевременной оптимизации.
- Не реализуй функциональность, которая может понадобиться только в будущем.

## Границы задач

- Выполняй исключительно явно поставленную задачу; не расширяй её объём по собственной инициативе.
- Не добавляй незаказанные функции и улучшения, не проводи попутный рефакторинг.
- Не меняй существующую архитектуру без необходимости, не перестраивай проект и не переименовывай файлы без прямой причины.
- Не изменяй файлы, не относящиеся к задаче.
- Из нескольких рабочих решений выбирай самое простое. Не предлагай альтернативные архитектуры без запроса.
- Не создавай дополнительные планы, исследования и отчёты.

## Код

- Используй Python, существующий `src`-layout, `uv` и `pyproject.toml` для зависимостей.
- Предпочитай стандартную библиотеку; добавляй внешние зависимости только при реальной необходимости.
- Пиши простой, читаемый код без лишних уровней абстракции.
- Не создавай базовые классы, фабрики, менеджеры, сервисы и интерфейсы ради предполагаемого будущего расширения.
- Не используй микросервисы, очереди задач и дополнительные инфраструктурные компоненты без прямого требования.
- Не добавляй избыточные комментарии и docstrings.
- Не дублируй логику, но и не создавай абстракции для одноразового кода.
- Не добавляй запасные реализации и fallback-механизмы без реальной необходимости.
- Сохраняй независимость Core от Telegram и конкретного ASR-движка.
- Не изменяй существующее поведение, если задача этого не требует.

## Тестирование и проверки

- Не создавай автоматические тесты, тестовые файлы, фикстуры, моки или тестовые данные.
- Не запускай pytest, unittest, линтеры, type-checkers и форматтеры.
- Не запускай сборки, benchmark и smoke-тесты, не проводи экспериментальные запуски для проверки гипотез.
- Не добавляй CI/CD и инструменты контроля качества.
- Не запускай транскрибацию тестового аудио самостоятельно и не выполняй проверки «на всякий случай».
- Разрешено изучать только относящиеся к задаче файлы и выполнять команды, необходимые для внесения изменений. Не запускать приложение, тесты, сборки, линтеры и дополнительные проверки без прямого запроса пользователя.
- Тестирование и проверку результатов пользователь выполняет самостоятельно. Если проверка не выполнялась, честно укажи это в итоговом сообщении.

Эти ограничения касаются действий агента. Сохраняй в рабочем приложении минимальную обработку ошибок и проверки недоверенных входных данных, необходимые для корректной и безопасной работы.

## Работа с зависимостями и файлами

- Не заменяй `uv` другими менеджерами пакетов и не создавай `requirements.txt`.
- Не обновляй существующие зависимости без необходимости. Не изменяй `uv.lock` без причины, связанной с зависимостями задачи.
- Не создавай дополнительные файлы документации без запроса. Не изменяй LICENSE.
- Не выполняй git commit, push или операции с удалённым репозиторием без прямого запроса.
- Не записывай токены, пароли и другие секреты в код или документацию; используй переменные окружения.

## Работа с неопределённостью

- Не исследуй несколько вариантов решения, если один очевидно удовлетворяет требованиям; не исследуй технологии без необходимости.
- Не додумывай требования и не реализуй предположения.
- При некритичной неоднозначности используй минимальное разумное решение.
- Если без уточнения невозможно корректно реализовать задачу, задай один конкретный вопрос.
- Не трать время на преждевременную оптимизацию и гипотетические проблемы.

## Формат завершения

Отвечай кратко:

1. Что реализовано.
2. Какие файлы изменены.
3. Что пользователь должен сделать вручную, если это необходимо.

Без длинных отчётов, самооценки, повторения технического задания и предложений дополнительных работ.
